

# Token Consumption: Measure, Predict, and Catch Surprises

> [!summary]
> Token consumption is the model-side work created by an agent run: fresh input, cache reads, cache writes, generated output, and sometimes hidden reasoning or intermediate turns. It is easy to undercount because agentic systems resend context, tool schemas, tool results, retrieved documents, and multi-turn history many times.

## Definition

Token consumption is the count of model tokens processed or generated during inference.

For an AWS AgentCore agentic project, the useful breakdown is:

| Metric | Meaning | Normalized field |
|---|---|---|
| Fresh input | New input tokens sent to the model that were not read from prompt cache | `fresh_input` from `inputTokens` |
| Cache read | Input tokens reused from prompt cache | `cache_read` from `cacheReadInputTokens` |
| Cache write | Input tokens written into prompt cache for possible later reuse | `cache_write` from `cacheWriteInputTokens` |
| Prompt total | All input-side work for the run | `fresh_input + cache_read + cache_write` |
| Output | Tokens generated by the model | `output` from `outputTokens` |
| Total | Prompt-side tokens plus output tokens | `prompt_total + output` |

The application should normalize usage this way instead of trusting a provider-specific `totalTokens` interpretation:

```text
Prompt = fresh input + cache read + cache write
Total  = Prompt + output
```

The implementation pattern is:

- AgentCore Runtime code should emit token metrics from the model client or framework result object for every completed run.
- AgentCore Harness integrations should preserve token usage from the Harness/Bedrock response stream metadata when it is provided.
- A shared normalization layer should map raw fields into `fresh_input`, `cache_read`, `cache_write`, `prompt_total`, `output`, and `total`.
- A separate cost layer should convert measured token buckets into list-price cost buckets, while keeping the measured usage separate from the price assumptions.

## Why It Matters

Tokens drive several different engineering and operating concerns:

- **Cost:** each input, output, cache-read, and cache-write bucket can have a different rate.
- **Latency:** long prompt processing and long output generation both slow the user-visible response, with output length often dominating streaming duration.
- **Context limits:** long sessions can fail or degrade when retained history, tool results, and retrieved context fill the model window.
- **Architecture comparison:** Harness and Runtime agents are only comparable if both report usage through the same normalized fields.
- **Caching honesty:** cache reads are savings; cache writes are an upfront cost that only pays back when the prefix is reused before expiry.

The most important rule is to separate measured usage from estimates. Token usage should come from the model, Harness, or Runtime response stream; the application may format and price it, but it should not invent cache-read or cache-write values.

## Which Use Cases It Bites First

In this section, **token pressure** means the token load that starts to make an agent harder to operate. It is not only "many tokens" in the abstract; it is the point where system prompts, user input, conversation history, retrieved chunks, tool schemas, tool results, cached prefixes, and generated output start pushing on cost, latency, or the model context window.

For example, a one-shot weather question has low token pressure. A long-running research session with retained chat history, browser extracts, retrieved memories, and several tool results has high token pressure even if the final answer is short, because the model still has to process all that surrounding context.

| Use case | First token pressure | Why |
|---|---|---|
| Long-context chat | Retained history | Every turn can resend more conversation state |
| RAG over large documents | Retrieved chunks | The answer may be short, but the prompt is large |
| Tool-heavy agents | Tool schemas and tool results | Schemas and observations repeat across cycles |
| Research agents | Agent cycles | Each step adds context, reasoning, and outputs |
| Browser agents | Extracted page content | Pages and screenshots can become very large prompt inputs |
| Structured output workflows | JSON schema and repair retries | Schema text and validation retries add hidden calls |
| Personalized assistants | Retrieved memories | Durable memory reads can expand the prompt every turn |
| Benchmark demos | Warm cache state | A cached run may look cheaper or faster than a cold architecture |

## How To Measure

Use the provider's response usage as the source of truth after inference.

For Amazon Bedrock message APIs, `TokenUsage` reports:

- `inputTokens`
- `outputTokens`
- `totalTokens`
- `cacheReadInputTokens`
- `cacheWriteInputTokens`
- optional cache details for writes by TTL

For preflight estimates, use Bedrock `CountTokens`. It returns the input token count that would be processed for the same `InvokeModel` or `Converse` request, using the selected model's tokenization rules.

Recommended measurement model:

| Stage | What to capture | Why |
|---|---|---|
| Before request | Estimated input tokens with `CountTokens` for large prompts | Prevent context-window and budget surprises before running the agent |
| During stream | Raw provider/runtime usage events | Preserve the measured source fields |
| After run | Normalized token buckets and list-price cost | Make Harness vs Runtime comparison consistent |
| Health-check | p50/p90/p99 token totals by workflow | Catch long-tail regressions that averages hide |

Percentile health-checks should be calculated per workflow, not across all traffic mixed together. For each workflow, collect many completed runs, compute `total = fresh_input + cache_read + cache_write + output`, sort those totals, then report:

| Percentile | Meaning | What it tells you |
|---|---|---|
| p50 | Half of runs used fewer tokens and half used more | The typical token footprint for that workflow |
| p90 | 90% of runs used fewer tokens and 10% used more | Expensive but still common-enough cases |
| p99 | 99% of runs used fewer tokens and 1% used more | Extreme long-tail behavior that averages hide |

Example workflow groups include simple weather lookup, multi-city comparison, browser research, RAG over a large document, and tool-heavy troubleshooting. The point is to catch cases where one workflow is usually cheap but occasionally explodes because the agent loops, retrieves too much context, browses too many pages, or generates an oversized answer.

Minimum run record:

```text
session_id
architecture: harness | runtime
model_id
inputTokens
cacheReadInputTokens
cacheWriteInputTokens
outputTokens
prompt_total
total
tool_calls
cycles
elapsed_seconds
estimated_token_cost
```

## How To Predict

For one model call:

```text
estimated_tokens =
  system_prompt
+ tool_definitions
+ retained_conversation_history
+ retrieved_context
+ tool_results
+ current_user_message
+ expected_output
```

For one agent run:

```text
run_tokens =
  sum(model_call_tokens for every agent cycle)
+ retries
+ fallback model calls
+ summarization or compaction calls
```

For cost:

```text
token_cost =
  fresh_input_tokens  * input_rate
+ cache_read_tokens   * cache_read_rate
+ cache_write_tokens  * cache_write_rate
+ output_tokens       * output_rate
```

Prediction should be done per workflow, not globally. A simple weather lookup, a RAG answer over a large document, and a multi-step research prompt have different token curves.

Useful estimation tiers:

| Tier | Method | When to use |
|---|---|---|
| Rough design estimate | Count prompt templates, expected retrieved chunks, expected cycles, and output budget | Architecture review before implementation |
| Preflight estimate | Bedrock `CountTokens` on the actual request shape | Large prompts, document uploads, health-check probes |
| Measured baseline | Actual stream usage from repeatable test prompts | Regression tracking and demo readiness |
| Production budget | p50/p90/p99 usage by route, tenant, and architecture | FinOps, quotas, alarms, and capacity planning |

## Where The Surprises Come From

### Long Contexts

Long context is expensive because it is not only "large once." In a multi-turn or agentic flow, the same context can be processed repeatedly across cycles.

Common growth sources:

- Full chat history retained turn after turn
- Retrieved document chunks appended without pruning
- Large tool results kept verbatim
- Browser page text or screenshots converted into context
- Debug traces or intermediate plans included in later prompts
- Multiple agents handing large summaries to each other

Prompt caching can reduce repeated processing when the prefix is stable, but it does not make context free and it does not help if the repeated portion keeps changing before the cache checkpoint.

### Multi-Turn Usage And Memory Growth

The ambiguous "memory" cost in agent systems has two meanings:

| Meaning | Token impact |
|---|---|
| Conversation memory inside the context window | Increases input tokens every turn unless summarized, pruned, or cached |
| Durable memory service or vector store | Adds retrieval, summarization, storage, and sometimes extra model calls |

The first one bites immediately in token metrics. The second one bites as a separate service and tool/retrieval cost, then can also increase tokens when retrieved memories are inserted into the prompt.

### Tool Schemas And Structured Outputs

Tool definitions, JSON schemas, examples, and structured-output instructions are part of the prompt side. They can be repeated on every model call. For tool-heavy agents, the schema can be larger than the user's question.

### Cache Writes Before Cache Reads

The first run with a stable prefix may write to cache. That write can be more expensive than normal input for some models or TTLs. The savings appear only when later runs produce cache reads.

This is why the health-check should look at:

```text
cache_read / prompt_total
cache_write / prompt_total
cache_savings
```

### Output Budgets

Output tokens are generated sequentially, so verbose final answers, hidden intermediate outputs, and unbounded reasoning loops can dominate latency and cost. Setting a clear maximum output budget is a FinOps control, not just a UX choice.

### Retries And Agent Cycles

One user request may cause several model calls:

```text
plan
tool call
tool result analysis
second tool call
final answer
retry on validation failure
```

The final response may look short while the run was expensive internally.

## AWS Option Vs Do-It-Yourself

| Dimension | AWS-managed option | Do-it-yourself option |
|---|---|---|
| Post-run measurement | Use Bedrock response usage fields, including cache read/write tokens when supported | Parse provider-specific responses and normalize them into your own event contract |
| Preflight token counting | Use Bedrock `CountTokens` for the selected model and exact request shape | Use tokenizer libraries or approximate counters, then reconcile against real usage |
| Prompt caching | Use Amazon Bedrock prompt caching for supported models and APIs | Implement prompt shaping, provider-specific cache controls, or self-hosted prefix/KV caching |
| Agent hosting metrics | Use AgentCore Runtime and CloudWatch/usage logs for runtime-side compute; keep token usage from Bedrock/model stream | Instrument your own host, queue, model client, and trace correlation |
| Observability | Use AgentCore/CloudWatch correlation plus application session IDs | Build request IDs, spans, dashboards, and cost joins yourself |
| Cost calculation | Use AWS list rates plus measured token buckets | Maintain your own pricing table, provider adapters, and billing reconciliation |
| Guardrails | Use model max-token settings, Bedrock quotas, CloudWatch alarms, and application-side max cycles | Build budget enforcement, truncation, compaction, retry limits, and alerting yourself |

Practical recommendation for an AWS AgentCore project:

```text
Use AWS-managed token reporting and CountTokens.
Keep application-owned normalization, cost explanation, regression tests, and health-check questions.
```

That gives the application provider-reported source fields while preserving an architecture-neutral comparison between Harness and Runtime.

## Validation Questions

Use these in the project health-check before presenting or deploying a new AgentCore workflow:

1. **Do we record token usage from the provider/runtime stream for every completed run?**
   The health-check should fail or warn if `inputTokens`, `outputTokens`, `cacheReadInputTokens`, or `cacheWriteInputTokens` are missing when the model path supports them.

2. **Can the application separate fresh input, cache read, cache write, prompt total, output, and total?**
   A single "tokens" number is not enough to debug cost or caching.

3. **Do repeated identical or near-identical prompts show cache reads after the first warm-up run?**
   If `cacheWriteInputTokens` appears but `cacheReadInputTokens` stays zero, the prefix may be unstable, below the model minimum, expired, or not actually cacheable.

4. **Does `prompt_total` grow across turns in long conversations?**
   If it grows without bound, the workflow needs pruning, summarization, compaction, or a stricter retrieval budget.

5. **Are tool schemas and tool results included in token estimation?**
   The user message alone is usually a tiny part of an agent prompt.

6. **Do we cap agent cycles, retries, retrieved chunks, and output tokens?**
   Each missing cap can turn one user request into many model calls.

7. **Can we run a preflight `CountTokens` check for large prompts before invoking the agent?**
   This catches context-window failures and obvious budget violations before spending on the full run.

8. **Do we compare cached cost against uncached cost?**
   Cache value should be measured as net savings after write cost, not assumed from the presence of caching.

9. **Do we track p90 and p99 token totals by architecture and scenario?**
   Agent token surprises usually live in the tail, not the average.

10. **Can we explain any Harness vs Runtime token delta from source fields?**
    The answer should point to prompt text, tool schema size, retained history, cache read/write behavior, cycles, or output length.

Minimum health-check gate:

| Check | Pass condition |
|---|---|
| Token fields present | Every completed run has `inputTokens`, `outputTokens`, and explicit cache read/write fields or a documented reason those fields are unavailable. |
| Prompt total bounded | `prompt_total` stays under the workflow budget at p90 and p99, not only on the median run. |
| Cache behavior explained | Cold and warm runs are labeled, and any cache write without later cache read has an identified cause or follow-up. |
| Loop budget enforced | Agent cycles, retries, retrieved chunks, and output tokens have explicit caps in both Harness and Runtime paths. |

## Implementation Notes

- Display prompt-side token buckets separately: fresh input, cache read, cache write, prompt total, output, and total.
- Treat the normalization function or adapter as the source of truth for cross-architecture comparison.
- Price measured token buckets separately, including cache read and cache write, instead of multiplying one total by one rate.
- Treat missing token usage as a data-quality issue, not as zero usage, unless the model/API path explicitly cannot emit the field.
- Label warm-cache and cold-cache runs separately in demos, benchmarks, and regression tests.
- If AgentCore Memory is enabled, separate memory service cost from context-window token growth.
